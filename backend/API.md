# Opti-Bot — API (для фронтенда)

Base URL (локально): `http://localhost:5000`

Все эндпоинты ниже — под префиксом `/api/v1`, кроме `/health*`.
Формат ошибок FastAPI по умолчанию: `{"detail": "..."}`.

---

## Уже работает

### `GET /health`
Проверка живости сервиса.
```json
{ "status": "ok" }
```

### `GET /health/deps`
Проверка подключения к Postgres/Redis.
```json
{ "database": "ok", "redis": "ok" }
```

### `POST /api/v1/whatsapp/webhook`
Внутренний эндпоинт — сюда стучится Green-API при новом сообщении в WhatsApp.
Фронтенду не нужен.

CORS открыт для всех origin (без аутентификации, хакатон-скоуп) — фронтенд может стучаться
напрямую с `localhost:5173`.

## Работает (было "в разработке" — теперь эндпоинты реальные, не только контракт)

### База знаний

Управление FAQ-записями (Этап 1 — бот отвечает из этой таблицы, если находит совпадение).

**`GET /api/v1/knowledge-base`** — список всех записей
```json
[
  { "id": 1, "question": "Как подать документы?", "answer": "Через личный кабинет на сайте.", "created_at": "2026-09-19T10:00:00Z" }
]
```

**`POST /api/v1/knowledge-base`** — создать запись
Запрос:
```json
{ "question": "Как подать документы?", "answer": "Через личный кабинет на сайте." }
```
Ответ: `201`, объект записи (как в списке выше).

**`GET /api/v1/knowledge-base/{id}`** — одна запись
Ответ: объект записи, либо `404`.

**`PUT /api/v1/knowledge-base/{id}`** — обновить запись (частично)
Запрос:
```json
{ "question": "Новый вопрос", "answer": "Новый ответ" }
```
Оба поля необязательны — можно прислать только одно.

**`DELETE /api/v1/knowledge-base/{id}`** — удалить запись → `204`

### Диалоги (для панели оператора)

Список переписок бота с пользователями WhatsApp, эскалация на оператора (Этап 3).

**`GET /api/v1/conversations`** — список диалогов (без истории сообщений)
```json
[
  {
    "id": 1,
    "chat_id": "77771320307@c.us",
    "escalated": false,
    "created_at": "2026-09-19T10:00:00Z",
    "updated_at": "2026-09-19T10:05:00Z"
  }
]
```

**`GET /api/v1/conversations/{id}`** — диалог с полной историей сообщений
```json
{
  "id": 1,
  "chat_id": "77771320307@c.us",
  "escalated": true,
  "created_at": "2026-09-19T10:00:00Z",
  "updated_at": "2026-09-19T10:05:00Z",
  "messages": [
    { "id": 1, "sender": "user", "text": "Здравствуйте, хочу поговорить с человеком", "created_at": "2026-09-19T10:00:00Z" },
    { "id": 2, "sender": "bot", "text": "Передаю ваш вопрос оператору...", "created_at": "2026-09-19T10:00:05Z" }
  ]
}
```
`sender` — один из: `user`, `bot`, `operator`.

**`POST /api/v1/conversations/{id}/reply`** — оператор отвечает вручную (уходит в WhatsApp через Green-API)
Запрос:
```json
{ "text": "Здравствуйте! Чем могу помочь?" }
```
Ответ: обновлённый объект диалога (как в `GET /{id}`) с новым сообщением от `operator`.

**`POST /api/v1/conversations/{id}/escalate`** — оператор вручную берёт диалог (даже если клиент
не просил) — бот перестаёт отвечать в нём. Ответ: объект диалога с `"escalated": true`.

**`POST /api/v1/conversations/{id}/resolve`** — снять эскалацию, вернуть диалог боту
Ответ: объект диалога с `"escalated": false`.

## Фронтенд подключён

`frontend/` смотрит на этот API через Vite-прокси (`/api` → `http://localhost:5000`, см.
`frontend/vite.config.ts`) — реального WebSocket нет, `Inbox` поллит `GET /conversations` раз в
5 секунд. Если бэкенд недоступен, фронт откатывается на локальную демо-симуляцию (это штатное
поведение, не баг). Маппинг бэкенд-схем на фронтовые типы — в `frontend/src/lib/backend.ts`.

Важные упрощения маппинга (бэкенд этого не хранит, значения выведены/захардкожены на фронте):
`visitorName` — это `chat_id` без `@c.us`, `institution`/`institutionKind` — статичная заглушка,
`stage` (`knowledge`/`ai`/`operator`) — грубо выведен из `escalated` (реальной разбивки KB/ИИ
бэкенд не хранит), `unread` — всегда `0`. Статистика на `/stats` пока не подключена к бэкенду —
там нет эндпоинта агрегации, страница работает на локальных demo-данных.
